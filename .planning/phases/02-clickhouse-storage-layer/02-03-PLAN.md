<objective>
Build the storage repository: the row POJOs that mirror the DDL columns (including the `SpanContext`-sourced identity columns), the `SpanRepository` seam (the read interface the Phase-4 query API will consume), and the client-v2 implementation — RowBinary batch inserts for `writeBatch`, the two-step `trace_id_ts`→`spans` lookup for `getTraceById` (STOR-02), the `agent_runs`-backed `listRuns`, and the point-lookup `getPayload` (STOR-03). </objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller (Phase 3/4) → SpanRepository | trace_id and filter values originate from external requests; untrusted input crosses into SQL here |
| repository → ClickHouse (HTTP :8123) | RowBinary inserts + parameterized queries |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-06 | Tampering | SQL injection via trace_id / RunFilter values in getTraceById/listRuns/getPayload | mitigate | Every user-controlled value is bound as a client-v2 `{name:Type}` placeholder — never string-interpolated into SQL (Task 2 acceptance grep). RowBinary typed POJO inserts mean writeBatch never builds INSERT SQL from values either. This is the primary storage-layer threat called out in the security model. |
| T-02-07 | Tampering | unbounded / oversized payload bodies written to ClickHouse | mitigate | The 256 KB-per-field cap + truncation contract (Phase-1 D-13) is honored at write time — PayloadRow carries `PayloadTruncated`/`PayloadOriginalSizeBytes`; the truncated-payload fixture verifies the cap round-trips. (Cap is applied by the producer mapping in Plan 04; the repository persists the already-capped body + metadata and the IT asserts it.) |
| T-02-08 | Information Disclosure | prompt/PII in persisted payloads | accept | Single-team self-hosted tool (REQUIREMENTS out-of-scope: auth/multi-tenancy); TTL (14-day) bounds retention; payloads kept off the hot path; convention already warns payloads may carry PII. No additional control for v0.0.1. |
| T-02-09 | Repudiation/Error-Handling | swallowed insert/query failures | mitigate | Expected DB failures return `Result.failure` (not silent success, not uncaught throw), so the Plan-04 writer can retry/backpressure on them rather than lose spans. |
</threat_model>
