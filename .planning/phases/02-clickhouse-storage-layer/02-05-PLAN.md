<objective>
Close the single blocker gap from 02-UAT.md: the ClickHouse schema fails to apply against a real ClickHouse (Code: 62 SYNTAX_ERROR), so all three storage integration tests fail at setup.

Root cause (already fully diagnosed in 02-UAT.md — do NOT re-investigate): `MigrationRunner.splitStatements()` splits each `.sql` file on `;` BEFORE stripping `--` line comments. The header comment on line 13 of `001_spans.sql` — `-- Pitfall 6: retention is TTL-only; never ALTER UPDATE/DELETE.` — contains a `;`. The naive `split(';')` cuts that comment in two; its second half (`never ALTER UPDATE/DELETE.`) no longer begins with `--`, escapes the per-line comment filter, and is prepended as garbage to the `CREATE TABLE spans (...)` statement. ClickHouse rejects it with unmatched parentheses and the schema never applies.

This defect was masked because the original executors ran against a broken Colima/QEMU Docker context and substituted grep-based "structural" checks for real container runs. This plan fixes the splitter, adds a fast Docker-free regression guard, and proves the three ITs GREEN against a REAL ClickHouse on the machine's healthy Docker Desktop context.

Purpose: Genuinely close SC1–SC4 with observed-green integration evidence (no grep-only substitution).
Output: Fixed splitter, new regression unit test, three storage ITs observed passing.
</objective>

  <behavior>
    - Given SQL whose comment contains a semicolon (e.g. a line `-- retention is TTL-only; never ALTER.` followed by a `CREATE TABLE t (a Int32) ENGINE = Memory;` statement), splitStatements returns statements where NO fragment contains comment text ("retention", "never ALTER") AND each returned statement has balanced parentheses (count of '(' equals count of ')').
    - Given the real `001_spans.sql` resource content, the single returned CREATE TABLE statement starts with `CREATE TABLE` and has balanced parentheses and contains no `--` text and no leaked `never ALTER UPDATE/DELETE.` fragment.
    - Given a multi-statement file, the number of returned statements equals the number of real (non-comment) `;`-terminated statements, ignoring trailing blank fragments.
    - Edge: a fully-commented file (only `--` lines) returns an empty list.
  </behavior>
  <action>
    Rewrite `splitStatements(sql: String): List<String>` so it strips `--` line comments BEFORE splitting on `;`, eliminating the leak where a semicolon inside a comment breaks the following statement (root cause per 02-UAT.md, line 13 of 001_spans.sql).

    Implementation approach (comment-strip-first, then split):
    1. First pass over the input by lines: for each line, drop the `--` line comment. Strip the comment portion even when `--` appears mid-line after SQL (not only full-line comments) — find the first `--` on the line and keep only the text before it, then keep the (possibly empty) remainder. Rejoin with `\n`. This guarantees no `--` and no comment text survives into the split phase, so a `;` inside a comment is gone before splitting.
    2. Then `split(';')` the comment-free text into fragments, `trim()` each, and `filter { it.isNotEmpty() }`.

    Note on string literals: the migration DDL in this repo contains no `;` inside SQL string literals (verify against the four `migrations/*.sql` files), so comment-stripping-before-split fully closes this gap. Add a brief KDoc note that the splitter assumes no `;` inside string literals (true for all current migrations) and that handling `;` inside literals would require a fuller tokenizer if that ever changes — do NOT over-engineer a SQL tokenizer for v0.0.1.

    Update the existing KDoc on `splitStatements` (and the class-level step-3 bullet that currently says "split the file on `;`") to reflect comment-stripping-first ordering, so the doc no longer describes the buggy order.

    Kotlin conventions (CLAUDE.md): no `var` (use functional `lineSequence()/map/joinToString/split/filter` as the current code does), no `!!`, keep it a pure function returning `List<String>`, ktlint-clean.

    Write the Docker-free regression test (Task is tdd) in the SAME commit-friendly cycle: create `MigrationRunnerSplitTest.kt` first capturing the <behavior> cases (it must FAIL against the current buggy splitter — semicolon-in-comment leaks comment text and unbalances parentheses), then apply the fix to make it pass. To exercise the private `splitStatements`, prefer the smallest viable seam: if `splitStatements` is `private`, promote it to `internal` (still hidden outside the module, satisfies "no public API expansion") OR extract the pure splitting logic into an `internal`/companion function the test can call directly. The test must read the real `001_spans.sql` from the classpath (`javaClass.classLoader.getResourceAsStream("migrations/001_spans.sql")`) for the real-fixture assertion, and use an inline SQL string for the synthetic semicolon-in-comment case.
