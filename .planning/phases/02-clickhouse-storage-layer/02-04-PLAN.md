<objective>
Build the batching write pipeline (D-08): the `AgentSpanRowMapper` that projects an `(AgentSpan, SpanContext)` pair into a `SpanRow` + `PayloadRow` (populating the identity columns from `SpanContext` and enforcing the 256 KB cap + truncation at write time), and the `SpanWriter` — a bounded coroutine `Channel` drained by one writer coroutine that flushes by count/time, retries failed flushes with bounded exponential backoff, and applies backpressure (producer suspends, never drops) when the buffer fills. The backpressure signal is exposed as a first-class API for the Phase-3 receiver. Prove sustained load keeps ClickHouse part counts bounded (SC4) via Testcontainers, and the flush/backpressure semantics via a MockK unit test.

`SpanContext` is the producer-facing seam the Phase-3 OTLP receiver will supply real envelope identity into: in Phase 2 the writer's callers (tests) mint it via SpanFixtures; in Phase 3 the receiver extracts it from the OTLP span envelope. `AgentSpan` alone cannot produce the mandatory TraceId/SpanId/ParentSpanId/Timestamp columns — `send` must carry the context.

Purpose: ROADMAP success criterion 4 — "writes flow through a batching pipeline (flush by count/time); sustained insert load keeps ClickHouse part counts bounded." This is the seam the Phase-3 OTLP receiver plugs into (transport-agnostic suspend send(span, context) + backpressure signal). Per-request inserts are the cardinal anti-pattern (Pitfall 1) — the batcher is day-one architecture.
Output: `AgentSpanRowMapper`, `BackpressureSignal`, `SpanWriter`, `SpanWriterTest` (unit), `PartCountIT` (integration).
</objective>
