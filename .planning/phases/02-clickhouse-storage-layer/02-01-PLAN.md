<objective>
Wave 0 for the storage layer: add every new dependency to the version catalog and the backend build, introduce the `SpanContext` envelope-identity carrier, and stand up the Testcontainers ClickHouse fixture + deterministic span fixtures that all downstream integration tests (`ClickHouseSchemaIT`, `SpanRepositoryIT`, `PartCountIT`) and the unit test (`SpanWriterTest`) depend on.

This is the FIRST storage code in the repo and the FIRST ClickHouse dependency — Testcontainers has no analog here yet, so the shared container + fixtures must be built before any DDL, repository, or pipeline test can run.

`SpanContext` is the one production type that lands in Wave 0 because both the test fixtures (Wave 1) and the mapper/writer (Wave 4) consume it: `AgentSpan` is a typed view of OTLP *attributes* only and deliberately carries NO `traceId`/`spanId`/`parentSpanId`/`timestamp` (those envelope fields are extracted in Phase 3). But the Phase-2 schema makes that identity structurally mandatory — `Timestamp`/`TraceId` in the spans `ORDER BY`, `toDate(Timestamp)` partition, `SpanId`/`ParentSpanId` columns, the `(TraceId, SpanId)` payload key, and `GROUP BY TraceId` in both MVs. `SpanContext` is the seam that supplies that identity; in Phase 2 it is minted by fixtures, in Phase 3 the receiver populates it from the real OTLP envelope.

Purpose: Establish the test seam against a real ClickHouse so success criterion 4 ("proven against a real ClickHouse instance via Testcontainers") and the EXPLAIN/part-count assertions of later plans have infrastructure to run on, AND settle the unrecoverable row/key identity shape (real TraceId/SpanId per span, never empty-string sentinels that would collapse every span into one key/partition).
Output: Catalog + build wiring; `SpanContext` (envelope-identity carrier); `ClickHouseTestSupport` (shared singleton container + Client factory); `SpanFixtures` (deterministic (AgentSpan, SpanContext) builder + multi-span single-TraceId helper).
</objective>
