## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| backend → ClickHouse (HTTP :8123) | DDL + future row inserts cross here; SQL execution surface |
| process env → ClickHouseConfig | Credentials enter the process from the environment, never from source |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-02 | Information Disclosure | ClickHouse credentials | mitigate | `ClickHouseConfig.fromEnv()` reads `CLICKHOUSE_PASSWORD`/USER/URL from env vars only; password has no literal default (Task 2 acceptance: `grep setPassword("` returns nothing). CLAUDE.md hard rule. |
| T-02-03 | Tampering | DDL execution via MigrationRunner | mitigate | Migration SQL is static project-owned resources (no user input concatenated into DDL); every statement is `CREATE ... IF NOT EXISTS` so a re-run cannot corrupt or duplicate schema; runner is convergent/re-runnable under ClickHouse's non-transactional DDL. |
| T-02-04 | Denial of Service | unbounded table growth / disk exhaustion | mitigate | Every table DDL carries a mandatory `TTL ... INTERVAL 14 DAY` (Pitfall 6); retention is TTL, never an unbounded insert-only table with no expiry. |
| T-02-05 | Tampering | future query parameters (trace_id/filters) flowing into SQL | mitigate | Schema/runner here use only static SQL; the parameterized-query contract (`{name:Type}` placeholders, never string concat) is established now and enforced in Plan 03's repository where user-controlled trace_id/filter values first appear. |
</threat_model>
