<objective>
Add the Phase-3 build dependencies (Ktor server, grpc-netty-shaded/stub/protobuf, otel test SDK) and build the transport-agnostic core of the OTLP receiver: the single `OtlpDecoder` (D-06) that turns an `ExportTraceServiceRequest` into `(AgentSpan, SpanContext)` envelopes, the `DecodeResult` accounting type (D-02), the `OtlpResponses.buildResponse` partial_success builder, and the env-sourced `ReceiverConfig`. The decoder's D-07 hex-id encoding is the load-bearing, silently-breakable contract — this plan pins it byte-for-byte against the Phase-2 `SpanFixtures` format and proves it with a round-trip unit test as the first risk-reducing task. This single decoder path is also the D-03 store-all path: every span (agent and non-agent) flows through `AgentSpanExtractor` here, with no span dropped and no separate generic-span table.

Purpose: Both transports (HTTP route in 03-02, gRPC service in 03-03) call this exact same decoder and response builder, so partial_success accounting and the `SpanWriter` hand-off are implemented ONCE. Getting the D-07 hex format wrong silently breaks `getTraceById` (Pitfall 1) — pinning it here, first, de-risks the whole phase.

Output: `ingest/OtlpDecoder.kt`, `ingest/DecodeResult.kt`, `ingest/OtlpResponses.kt`, `ingest/ReceiverConfig.kt`, plus `OtlpDecoderTest.kt` + `OtlpRequestFixtures.kt`, and the catalog/build-file dependency additions.
</objective>

| Boundary | Description |
|----------|-------------|
| OTLP wire → OtlpDecoder | Untrusted protobuf `ExportTraceServiceRequest` (after parse) is walked; attribute values are attacker-controlled. |
| Env → ReceiverConfig | Operator-supplied port/size knobs; not a network boundary but bounds-checked. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Tampering | OtlpDecoder over malformed/mistyped attributes | mitigate | Decode goes through `AttrView`/`AgentSpanExtractor` which NEVER throw and return null on wrong variant (Phase-1 V5 control, already tested); decoder mirrors the never-throw invariant — one bad span → `rejected++`, never an exception (D-02). |
| T-03-02 | Denial of Service | OtlpDecoder building giant attribute strings | accept (bounded downstream) | No size check in the decoder by design (D-02 truncate-not-reject); the Phase-2 `AgentSpanRowMapper` 256 KB cap truncates downstream of `SpanWriter.send`. The transport-level body/message-size caps (03-02 HTTP, 03-03 gRPC) bound total request size before decode. |
| T-03-03 | Denial of Service | ReceiverConfig misconfiguration (port 0, negative caps) | mitigate | `init {}` `require()` validates ports (1..65535, http≠grpc) and positive byte caps — fails fast at construction. |
| T-03-SC | Tampering | npm/pip/cargo installs | mitigate | No npm/PyPI/cargo installs this plan; all new deps are first-party OpenTelemetry/gRPC(Google)/Ktor(JetBrains)/protobuf(Google) Maven Central artifacts (RESEARCH §Package Legitimacy Audit: all OK, no [ASSUMED]/[SUS]). No legitimacy checkpoint required. |
